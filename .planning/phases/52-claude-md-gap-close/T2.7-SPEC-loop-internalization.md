## 第一部分:ralph-loop

### 现状三段

1. **上游依赖**:`manifests/tools/ralph-loop.yaml` 装 `ralph-loop@claude-plugins-official`。`git_ref` 钉在 5 月、`last_check: 2026-05-11`、`stability: beta`;description 自述 **"Windows requires jq + Git Bash"**;install method 是 `cc-plugin-marketplace` 配一条 REPL slash command,manifest 头部那句「headless 安装机制未定,Phase 1.2 会用 (A)(B)(C) 之一解决」从 v0.1 至今未解决。
2. **harnessed 自己的机器**:`ralphLoop.ts`(`isComplete` 4 层双信号)+ `promiseExtract.ts` + `completionSchema.ts` + `defaults.yaml:11` 的 `ralph_max_iterations` —— 齐全、有单测,但唯一消费者是 `run.ts:378` / `sdkSpawn.ts`,即所有 SKILL 明令禁用的 `harnessed run` 路径。**与审计 S1 同病:built-but-unwired。**
3. **活路径上的相邻件**:`checkpoint.ts:507` BREAK-LOOP(失败次数达 `LOOP_THRESHOLD` 熔断)+ `injectState.ts:124` 每回合提示。数的是**失败次数**,不是「朝完成推进的迭代」。

### ECC 给出的关键论据(实拉,带出处)

**A. 自评不可信,这是 ECC 整套设计的首要论断。**

`skills/gan-style-harness/SKILL.md:15-17`:
> When asked to evaluate their own work, agents are pathological optimists ... But engineering a **separate evaluator** to be ruthlessly strict is far more tractable than teaching a generator to self-critique.

配套三条硬约束:generator 不判(`agents/gan-generator.md:29` "Don't self-evaluate")· evaluator 不修自己评过的东西(`skills/gan-style-harness/SKILL.md:256`)· `loop-design-check/SKILL.md:85` "Build may not edit the acceptance conditions to pass"。

**这条直接击中 ralph-loop 的要害**:`<promise>COMPLETE</promise>` 是**被评者自己输出的字符串** —— 结构上就是自评。ralph-loop 的确定性只保证「字符串确实出现了」,不保证「事情真做完了」。

**B. 一个停机理由不够,必须有阻尼。**

`gan-harness.sh` 有三个独立停机理由:达标停(`:218` `score_passes`)· **无进展停**(`:224-235`,第 3 轮起单轮涨幅 ≤ 0.2 计一次、连续 2 次即停)· 预算停(`:157` for 上限)。

`skills/loop-design-check/SKILL.md:87-89` 把它抽象成原则,并且用了一个讽刺的名字:
> Retry cap, hard stop, human flips the last switch = damping. **Negative feedback with no damping oscillates** (the Ralph-Wiggum loop: spinning in place, burning tokens).

ralph-loop 只有「预算停」一种,分数卡死也会把迭代烧完。

**C. 对账优先于断言(done-criterion 可被博弈)。**

`skills/loop-design-check/SKILL.md:56`:
> **Prefer reconciliation over assertion for the done-criterion** — anchor to external fact (golden sample / upstream total / financial tie-out) before your own assertions. "All tests pass" can be gamed (loosen asserts, fake mocks, swallow exceptions); "diff vs the reference < 0.01" can't.

**D. done-criterion 必须配 boundary(Goodhart 抗体)。**

`skills/loop-design-check/SKILL.md:105` 的最坏崩法表:
> (worst) Only gates on "all tests pass" → **agent deletes the tests** | Is there a boundary ("what it must NOT do")? Or only a done-criterion? | Done-criterion **+ boundary** together

改法示例(`:121`):`all tests green AND no test file deleted or weakened AND coverage not lowered AND a change-list produced`。

**这条打到 harnessed 自己身上**:4.33.0 刚加的 `tdd-evidence.md` 门是**纯 done-criterion,没有 boundary** —— 「写一个 tdd-evidence.md」这件事本身可以被敷衍(空文件、复制粘贴、编造红→绿)。见下方 D-4。

**E. 机械门与推理门分层,且机械门要克制。**

`skills/delivery-gate/SKILL.md:11-17` 的分工:Stop hook 只做 deterministic checks(mtime / disk / transcript 正则计数),内容质量交推理门;`:28` 明确说明**正则启发式故意只警告不阻断**,因为会误报;`:108-110` 承认局限「enforces the **habit** of touching learning libraries, not the **quality** of what was recorded」。

这与用户已裁决的 D1 混合方案完全同向 —— 可作为 ADR 的外部佐证。

**F. 跨轮状态一律落盘 + 指针注入,不靠 prompt 累积。**

固定目录 + 零填充编号(`feedback-%03d.md`)+ 每轮全量 log + 每轮 git commit;驱动器只注入一句「去读 feedback-NNN.md」,且注入前 `-f` 验过文件存在(`gan-harness.sh:164-173`)。每轮每角色都是**新 `claude -p` 进程**(`:169,186`),context 天然隔离。

### ECC 的脆弱处(明确不照搬)

1. **分数提取靠三层正则抠 markdown 表格,抠不到默认 `0.0`**(`gan-harness.sh:61-69`)。格式漂移 → 静默当不及格。**讽刺的是**:这使得 ECC 的「确定性阈值比较」建立在一个不确定的输入上 —— ralph-loop 的字符串匹配在这点上反而更稳(不会读错分数)。
2. **FAIL 也 `exit 0`**(`:285-299` 全程无 `exit 1`,只有 planner 缺 spec 那一处例外 `:141-146`)→ CI 里挂不住,失败不向上游传播。
3. **同一循环两份实现**:`scripts/gan-harness.sh`(bash 确定性)与 `commands/gan-build.md`(prose 伪代码,while/比较/break 由主 session「假装执行」)。两条链默认模型还不一致(shell `opus` vs agent frontmatter `sonnet`)。
4. **GAN 内建假设是 web 应用**(`DEV_PORT` / `DEV_CMD` / evaluator 用 Playwright 点页面);适用范围自述很窄(`gan-style-harness/SKILL.md:30-35` 排除 quick single-file fixes / simple refactoring / 已有测试的明确任务)。
5. **`loop-operator` 等于没实现**:`agents/loop-operator.md` 全文 40 行 prose,"no progress across two consecutive checkpoints" 里的 checkpoint 与 progress 都无度量定义。

### ralph-loop 独有的优势(诚实记录,摘除时会损失)

1. **通用性** —— 承诺字符串与任务无关,任意子任务可用;ECC 的 GAN 绑 web 应用。
2. **单执行单元即可** —— 包一层就完事;ECC 最少要 2 个角色 + 外部驱动器。
3. **完成判定不会读错** —— 见脆弱处 1。
4. **统一入口 + 稳定 flag**(`--max-iterations` / `--completion-promise`);ECC 的循环能力散在 8 处且无统一入口。

### 设计:三步,顺序不可换

#### 第一步 — 把保证搬到活路径(内化,不依赖任何上游)

映射关系:harnessed 的基座**已经齐全**,缺的是接线与两个新概念。

| ECC 机制 | harnessed 已有基座 | 要做的 |
|---|---|---|
| 独立判定者(不自评) | `verify` stage 各 sub 本就是独立 subagent,context 隔离 | **verify 结论要能喂回 task 循环** —— 目前 verify 通过与否不驱动重跑 |
| 产物存在性门 | `artifacts_expected` + `checkArtifacts` fail-closed exit 1(4.33.0 已用于 task-test) | 已有,复用 |
| 预算停 | `defaults.yaml:11 ralph_max_iterations` | **在 ledger 里执行**(现在只是模板值,无执行者) |
| 失败熔断 | `checkpoint.ts:507` BREAK-LOOP + `LOOP_THRESHOLD` | 已有 |
| **无进展熔断(阻尼)** | 无 | **新增** —— ledger 记每轮的「进展度量」,连续 N 轮无进展即熔断 |
| 跨轮状态落盘 | ledger `current-workflow.json` + phase 目录产物 | 已有;需明确「上一轮反馈」的落点与指针注入(`injectState` 已是注入通道) |
| 承诺提取 | `promiseExtract.ts` / `isComplete` 4 层 | **搬到 `checkpoint complete` 校验**(从死路 `run.ts` 移出) |

**D-1 承诺校验落 `checkpoint complete`**。`checkpoint complete <sub>` 已有 fail-closed 证据门;把 `isComplete` 接进去,作为「done 之前必须满足」的一部分。复用现成实现与单测,不重写。

**D-2 迭代预算在 ledger 执行**。`ralph_max_iterations` 从模板值变成真预算:ledger 记 per-sub attempt 计数(BREAK-LOOP 已在数,复用同一计数源),超预算 → 与 BREAK-LOOP 同款的 breadcrumb + 拒绝再 spawn。

**D-3 新增无进展熔断(ECC 的 plateau 对应物)**。harnessed 没有「分数」这个连续量,所以进展度量要另找锚。候选(需裁决,见 OQ2):(i) 证据产物的 diff 是否变化;(ii) 失败测试数是否下降;(iii) 每轮要求 subagent 报一个结构化进展字段。**不引入 rubric 打分** —— ECC 的分数来自模型自述,再被三层正则抠出来,是它最脆的一环。

**D-4 给 done-criterion 配 boundary(ECC 论据 D 的直接应用)**。4.33.0 的 `tdd-evidence.md` 是纯 done-criterion。补 boundary 的候选:测试文件未被删除或弱化 · 断言数未下降 · 产物非空且含红→绿两侧。**这条独立于摘除 ralph-loop,本身就该做** —— 它修的是我们刚交付的门的可博弈性。

**D-5 分层遵循 D1 裁决**:确定性部分(计数、产物存在、文件未删)进 CLI/ledger;质量判断留 prompt 注入。参照 ECC 的 `delivery-gate` 自述边界:机械门守习惯,不守质量。

#### 第二步 — `/goal` 从 tier 2 升为「可用时的便利」,不是保证承载者

**前置必须实拉验证**:`/goal` 的可用性与行为目前在仓内只有 ADR-0036 自述背书。按项目铁律(上游断言必须实拉验证)要真查一次。已知限制来自仓内 SKILL 文本自述:**single-slot per session,嵌套会覆盖外层**(`workflows/auto/SKILL.md:132`)—— 这对多层编排是实际约束。

#### 第三步 — 摘依赖

删 `manifests/tools/ralph-loop.yaml`;capability 从 `impl: plugin` 改为 harnessed 自有机制(形态待定,可能类似 `karpathy-guidelines` 的 `impl: harnessed-bundled` + 指向内部实现的 ref);改 ADR-0036 的三级链;连带 base manifest 计数(现 13,有测试断言)与 README。

## 第二部分:karpathy-skills(近乎纯减法)

### 现状:已经内化完了

`capabilities.yaml:627-633` 的 `karpathy-guidelines` 是 `impl: harnessed-bundled` + `cmd: '<not-applicable-behavioral>'` + `discipline_ref: workflows/disciplines/karpathy.yaml`;那份 discipline 有 5 条规则,且**全部 28 个 workflow** 通过 `disciplines_applied` 引用它 —— 走 `buildDisciplinesSection` 活路径。仓内**没有任何地方调用上游的 slash command**。所以 `manifests/skill-packs/karpathy-skills.yaml` 装的 plugin 已是冗余。

### 摘除前置:capability description 在超额声称

description 写「4 心法 + ≤200L hard limit + **no-feature-creep + trust-internal-code + no-comments-default**」,而 5 条规则是 `think-before-coding` / `simplicity-first` / `surgical-changes` / `goal-driven-execution` / `file-length-200-hard-limit`。

- `no-feature-creep` ≈ 被 `goal-driven-execution`(不夹带无关重构)覆盖一半
- **`trust-internal-code` 缺失**
- **`no-comments-default` 缺失**

直接摘上游会丢这两条思想。**补齐 discipline 是摘除的前置条件,不是可选项。**(`no-comments-default` 与项目现有代码风格是否冲突需确认 —— 仓内注释密度很高,这条规则若照搬会与既有代码基线矛盾,见 OQ3。)

### 摘除步骤

补两条 discipline 规则(+ zh-Hans sibling)→ 修正 description 与规则对账 → 删 manifest → capability 保留(它已是 bundled 形态,不需要动 impl)→ base manifest 计数与测试断言同步。

## Open Questions

- **OQ1 三步走还是只做第一步?** 第一步(保证搬到活路径 + boundary)有**独立价值**,不摘依赖也该做。第三步的收益主要是去掉 Windows 的 jq/Git Bash 门槛与一个装不上的安装路径。是一次做完,还是先做第一步、摘除缓一版?
- **OQ2 无进展熔断的进展度量取哪个?**(i) 证据产物 diff 变化 —— 最确定性但可被「改一个字」绕过;(ii) 失败测试数下降 —— 语义最准但只适用有测试的子任务;(iii) subagent 报结构化进展字段 —— 通用但是自述(踩 ECC 的自评坑)。倾向 (i)+(ii) 并存:有测试用 (ii),否则退 (i);**不用 (iii)**。
- **OQ3 `no-comments-default` 照搬还是改写?** 上游 karpathy 主张默认不写注释;而本仓注释密度很高(yaml 与 TS 都大量解释性注释,且这些注释是**普通用户理解 bundled 资产的唯一途径**)。照搬会与既有基线和「资产要自解释」的需要矛盾。倾向改写成「注释解释 why 不解释 what;不写与代码重复的注释」这类可与现状共存的表述。
