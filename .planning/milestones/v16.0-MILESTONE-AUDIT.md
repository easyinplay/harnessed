`isNestedHarnessContext()` 挡掉,所以 `codex exec` 子进程路径补的是 CI / headless;
交互面靠 Phase 65 的正文指挥模型自己用宿主原语。两者不是同一条路的两种实现。

## 立项前提被推翻 / 更正的(五条,均显式记录未静默改写)

1. **SPEC 的「`sdkSpawn` 宿主层」说法不准确**(Phase 66 F2b)。claude 侧是 in-process SDK `query()`,
   codex 侧只能是子进程 —— 不是给一个函数加分支,是两条并列路径。
2. **agents toml 与 `codex exec` 是两套机制**(F1 + F2)。`codex exec` 不能指定 agent role
   (`--help` 只有 `-p, --profile`,那是 config profile);agents toml 的价值落在会话内 `spawn_agent`。
3. **`spawn_agent` 的参数签名我写错了并已更正**(Phase 65 F14,commit `31ea64d`)。上游有两个构造函数:
   v1 的 required 是 `None` 且**没有** `task_name`,`task_name` 是 v2 才加的;本机 `multi_agent_v2 = false`
   → v1 生效。我读源码时把 v2 的签名当 v1,**已经写进产品正文并发了版**,靠 Phase 66 T0.4 的实测抓回来,
   发版前修掉(只动 codex 列,claude 金标零差异)。四个带命名参数的调用点是**重写**而非机械替换 ——
   `agent_type: <sub>` 会是一条保证报错的指令,因为 harnessed 还不为 sub 写 role toml。
4. **SPEC 的 236 处基线不完整**(Phase 65)。实际四个交付面 450+,维护者拍板全纳一次做干净;
   我自己的分类规则与「generateCommands 与 rewrite 脚本保持 lockstep」那句注释也各被证否一次
   (逐字比对发现两侧已漂移 5 处)。
5. **goal 是 ADR-0039 删掉的东西**(F2d)。删除理由正是「原生 `/goal` 从未被实证」,codex 侧 TUI
   可见性同样未实证 → 维护者裁定移出本 phase,进 TODOS 并附可执行实测步骤。

## Lessons(方法论层,进 RETROSPECTIVE 的候选)

- **「已实现」不等于「可达」。** T2/T3 交付了模块却无调用方;发版时如实按 built-but-unwired
  排除在 CHANGELOG 之外,随后补 T3b 接线。这个模式在本项目反复出现,值得每次交付时主动问
  「用户从哪进得去」。
- **一处修完要扫姐妹面。** Phase 64 修了 `ccPluginMarketplace` 的凭据备份,两个结构同形的
  MCP 安装器没扫到,整整两个 phase 后才由收口审计抓出。修完一条边界后应按**机制**(谁调用
  `backup()` 且 target 可能是敏感文件)而不是按**文件**再搜一遍。
- **给 subagent 的约束若引用项目记忆,先确认那条规则在当前上下文适用。** Phase 65 批 C 把
  「改 TypeBox schema 必须跑 `build:schema`」写进 brief,但那条针对 manifest schema ——
  代价是两次 8 小时空转。诊断靠进程级证据(无新起子进程)+ 最小任务探针(单任务 20 分钟跑完)
  区分「机制坏了」与「brief 坏了」。
- **重 golden 测试必须自带文件级 timeout。** 同一形状在本 milestone 内出现三次;判据是
  单跑绿 + `--no-file-parallelism` 绿 + 报 timeout 而非断言失败 → 负载竞争,去翻那个 commit 白费功夫。
- **发版核实口径用 registry 直查。** `npm dist-tag ls` 读本地 CLI 缓存,刚发完会显示上一版。
  权威顺序:publish run 日志 → `curl` registry `dist-tags` → `npm view <pkg>@<ver>`。
